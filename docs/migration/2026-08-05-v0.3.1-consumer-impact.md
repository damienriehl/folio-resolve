# Consumer impact — the 2026-08-05 fix series

**Read this if you are about to bump a consumer's `folio-resolve` pin, regenerate a golden
capture, or explain why a tagging run's output changed.** It was written cold-readable: every
factual claim carries a `file:line`, and everything unverified is named as such in §8.

---

## 0. TL;DR

- **Eight repos were inventoried as candidate consumers; four actually depend on folio-resolve**
  (`folio-mapper`, `folio-enrich`, `folio-insights`, `alea-intake`). `mootloop`, `clio-skills`,
  `generative-folio`, `folio-api`, `books`, `book-indexer`, `second-brain`, `dev-twin`,
  `folio-python`, `folio`, `folio-insights-sources` do **not**.
- **The most severe finding is `sources.py`, and it lands on exactly one consumer: `folio-insights`.**
  It is the only repo in the cockpit that calls `SourceClassifier`
  (`folio-insights/src/folio_insights/pipeline/stages/folio_tagger.py:815`). There the bug had **two**
  effects, not one: eligible body units were silently emitted with `folio_tags = []`
  (`folio_tagger.py:149-158`), **and** the same units were harvested into the corpus **domain prior**
  as if they were metadata (`folio_tagger.py:376-387`) — so the bug both suppressed tags and
  polluted the prior that steers the judge. **It is confirmed live in real output:** in
  `output/uat_ta_ch04_v8/extraction.json`, **5 of 5** units the metadata gate excluded were false
  positives, every one a Federal Rules of Evidence citation, in the chapter titled *Evidence and
  Objections* (§4.1a). And folio-insights' one regression test over this behavior is structurally
  incapable of detecting it (§4.1b).
- **The second-most consequential finding is `scoring.generate_search_terms`.** Its ordering is now
  deterministic, which folio-resolve's own `docs/migration/SCHEDULE.md:107-116` predicted "would
  invalidate folio-enrich's and folio-mapper's committed golden captures." Measured: it does, but
  only barely — 1 of 22 rows in folio-mapper's capture, 1 of 24 search-driven rows in folio-enrich's.
- **`folio-mapper` and `folio-enrich` are already running the new code** via editable installs
  pointing at the working tree, and both suites are green against it (520 and 889 passing).
  `folio-insights` and `alea-intake` run PyPI wheels **locally** — but folio-insights' *deployed
  images* are unpinned and already resolve 0.3.0 (§6.3), so "not yet exposed" is true of the dev
  venvs only.
- **One genuinely breaking change exists but hits nobody today:** `FeedbackStore` now raises
  `ValueError` on ids that are not `[A-Za-z0-9][A-Za-z0-9._-]*`. No consumer imports
  `folio_resolve.annotate`.
- **Four lockfile/venv/image drifts were found**, each of which moves a consumer's library version
  with no pin edit. The worst: **folio-insights' container images install folio-resolve unpinned
  from `pyproject.toml`** (`Dockerfile:43`, `Dockerfile.web:58`), so the sole consumer of the
  headline bug will pick up the fix on its next build with no review. See §6.

`OntologyBehavior(concept_exclude_substrings=("dupe",), concept_exclude_prefixes=("zzz",))`:

```
NEW  excludes_concept_label("Dupe Concept") -> True    ("ZZZ Placeholder") -> True
```

**F13 — search-term order.** The change is `sorted(content, key=len, reverse=True)` →
`sorted(content, key=lambda w: (-len(w), w))`, and `for w in content:` → `for w in sorted(content):`.

Measured on 3,219 synthetic multi-word legal phrases (2–4 content words drawn from a 34-word legal
vocabulary), comparing the old algorithm to the new **at the same interpreter hash seed**:

| seed | phrases whose emitted **order** changes | membership identical? |
|---|---|---|
| `PYTHONHASHSEED=0` | 1067 / 3219 (**33.1%**) | yes, all |
| `PYTHONHASHSEED=1` | 979 / 3219 (30.4%) | yes, all |
| `PYTHONHASHSEED=7` | 1148 / 3219 (35.7%) | yes, all |

Isolated at seed 0: the content-word tie-break alone accounts for 26.0%, the expansion-loop sort
alone 13.3%.

> **The single most important fact about F13:** the **set** of emitted terms never changes — only
> the order. Drift can therefore only materialise where a consumer lets order matter: a result
> limit, a truncation, a per-branch cap, or a tie-break among equally scored candidates. This is why
> the measured real-corpus impact (below) is far smaller than 33%.
>
> **And pinning `PYTHONHASHSEED=0` does not make a capture safe.** Seed-0 set order is not
> alphabetical, so a capture taken at seed 0 under the old code still disagrees with the new code.

## 4. The findings, in order of severity

### 4.1 — F1 `sources.py`: folio-insights, and only folio-insights

**One call site in the entire cockpit.** A repo-wide grep for `MatchPipeline`, `SourceClassifier`,
`classify_source`, `SourceType`, `section_label` across `folio-mapper`, `folio-enrich`,
`folio-insights`, `alea-intake`, `mootloop`, `clio-skills`, `generative-folio`, `folio-api`
(excluding `.venv`/`.git`/`node_modules`) returns exactly four lines, all in one file:

```
folio-insights/src/folio_insights/pipeline/stages/folio_tagger.py:815:  from folio_resolve import SourceClassifier
folio-insights/src/folio_insights/pipeline/stages/folio_tagger.py:819:      classifier = SourceClassifier()
folio-insights/src/folio_insights/pipeline/stages/folio_tagger.py:821:      section_label = " > ".join(unit.source_section) if unit.source_section else ""
folio-insights/src/folio_insights/pipeline/stages/folio_tagger.py:822:      return bool(classifier.is_taggable(section_label, unit.text or ""))
```

Note what is passed as `text`: **`unit.text`** — the unit's whole body, not a heading. So the
`len(text) < 200` guard applies to real prose, which is exactly the population the bug was built to
misjudge.

**The bug had two effects in folio-insights, not one.**

1. **Tags suppressed, with a misleading lineage record.** `folio_tagger.py:147-158`:

   ```python
   for unit in job.units:
       if not self._is_taggable_source(unit):
           unit.folio_tags = []
           record_lineage(unit, stage="folio_tagger", action="skip",
                          detail="metadata-as-signal: mapped to prior, not emitted as insight")
           continue
   ```

   A misclassified body unit therefore did not merely produce no tags — it produced an audit trail
   *asserting* it was metadata. Anyone auditing the run would have read the lineage and agreed.

2. **The domain prior was polluted.** `folio_tagger.py:374-387`, the pass that builds the corpus
   prior, uses the **inverse** of the same predicate:

   ```python
   harvested: Counter[tuple[str, str]] = Counter()
   for unit in job.units:
       if self._is_taggable_source(unit):
           continue
       mappings = self._ruler_mappings(unit.text, aho_matcher)
       for iri, label in mappings:
           harvested[(iri, label)] += 1
   ```

   Body units misread as metadata were run through the entity ruler and their concepts were counted
   into the frequency counter that produces the corpus subject tags. Because the misclassified
   population is *dated, cited, statute-referencing prose*, the prior was being steered by the most
   substantive units in the corpus — the opposite of the design intent, which was to harvest the
   copyright page. The `DomainPrior` then threads into the judge (`domain_prior.as_judge_context`),
   so the contamination is second-order: it moved judged scores on units that were tagged normally.

**Direction of the change:** units that previously produced no tags will now produce tags, and the
prior will be built from a smaller, genuinely-metadata population. Both are **corrections**. But
both are visible output changes, and the prior change means *even units that were never
misclassified can now be judged differently*.

**One nuance that makes this worse than the `MatchPipeline` case:** folio-insights calls
`SourceClassifier` **directly**, not through `MatchPipeline` (0 hits for `MatchPipeline` across
`src/ tests/ api/ scripts/`). `MatchPipeline.match` only consults the classifier when
`section_label` is non-empty (`src/folio_resolve/pipeline.py:193`); `_is_taggable_source` has no such
guard. **In folio-insights the ISBN heuristic fires even on units with no section label at all.**

### 4.7 — F14 `word_overlap` accumulation order: a fourth consumer row of dashes

**Added 2026-08-05, after the exhaustive determinism sweep that followed F4 and F13.** Two
hash-seed bugs in one pass implied the class was not exhausted, and it was not.

`_directional_overlap` ran `matched += best` while iterating `source`, a `set`. Float addition is
not associative, so the returned overlap depended on `PYTHONHASHSEED`. Unlike F13 this is **not**
confined to an opt-in path: the per-word credits `0.8` (prefix match) and `0.7` (4+ char common
prefix) are ordinary partial-match outcomes, and **four** mixed credits already split the sum.

```
word_overlap(content_words("contract defense settlement pleading"),
             content_words("contracts defendant settle pleadings"))
seed 0 -> 0.7750000000000001     seed 1 -> 0.7749999999999999
```

**Why every consumer cell is nonetheless a dash.**

1. **No consumer imports `word_overlap`.** Per §2b the scoring imports are `SEARCH_STOPWORDS`,
   `LEGAL_TERM_EXPANSIONS`, `BRANCH_SIGNAL_WORDS`, `compute_relevance_score`, `content_words`,
   `generate_search_terms`, `tokenize` — `word_overlap` appears in none of the four repos. It is in
   `__init__.__all__`, so an **external** consumer of the published wheel could be exposed; no
   cockpit one is.
2. **Through `compute_relevance_score` the drift is absorbed by `round(final, 1)`.** Measured:
   **251,160** realistic legal query/label pairs (4–7 content words drawn from a 32-word vocabulary
   of near-miss legal pairs), swept over seeds 0–11, at three `specificity_penalty` weights and with
   and without a definition. **65 pairs** have a seed-varying raw `word_overlap`; **0 pairs** have a
   seed-varying rounded score. So no ranked output, no truncation and no tie-break can move.
3. **The v0.3.0 golden no-drift table is untouched** (`tests/test_scoring.py`), and a
   61-seed differential probe over every public entry point is byte-identical pre-fix vs post-fix on
   everything except `use_vectors=True` raw floats, which move by 1 ULP.

**`math.fsum` was considered and rejected.** It is order-independent by construction, but it
disagrees with sequential `+=` on **594** of the default-path value multisets at n≤12 — adopting it
*would* have moved the golden table and every consumer's scores. Sorting `source` cannot, because
the default-path sum is order-invariant for the multisets that reach it; it fixes the accumulation
