# Label-blind passage generation

This directory defines the host-side contract for producing candidates that later enter the U5
synthetic-corpus workflow. Generation and grading are separate trust domains.

## Sandbox contract and evidence

Each generator worker runs in a fresh sandbox. Its only allowlisted inputs are one derived
assignment (document kind, jurisdiction, fictional scenario, length, register, no-match flag and
assignment ID), `prompt_template.md`, and its empty output directory. The label dictionary, gold
records, grader code, prior corpus, ontology files, branch targets, and complete quota table are
denied. Although the quota file is an orchestrator input, it is never mounted or passed to a
generator; the dispatcher derives label-blind assignments from its document section host-side.

Every run must write an input-file manifest generated by
`folio_eval.generation.input_manifest`. It records the SHA-256 of every file visible as worker
input. Store that manifest beside the run outputs so reviewers can prove the allowlist after the
fact. An undeclared input or a hash mismatch invalidates the run.

`render_prompt` is the final dispatch gate. It refuses ontology branding, identifier terminology,
links, and every public top-level branch name after substitution. This catches leakage introduced
by either a template edit or assignment text.

## Dispatch

Fan out assignments through the cockpit `agents/worker-wrapper.sh`; use one deterministic output
name per assignment as specified by the template. The dispatcher passes only the derived
assignment, the template, and the output directory. Worker logs and manifests belong under the
run output directory. `.codex/` is runtime state and is never a deliverable path.

The scoreable targets total 240 passages and the separate no-match targets total 30. The eight
document kinds span litigation, contracts, corporate, regulatory, intellectual-property, real
estate, employment, and estate-planning material, with multiple jurisdictions in each family.
Branch targets are host-side planning and post-grading coverage checks; they are not generation
instructions.

## Handoff to U5

Independent graders add `gold_labels`, resolved `gold_iris`, verification state, and an auditable
`provenance.branches_by_iri` mapping to each `SyntheticItem`. Before grading, `fill_report` can
measure only document-kind fill. After grading, it derives branch fill from each gold IRI and that
mapping. No-match items set `provenance.no_match` to `true` and retain empty gold fields.

After adjudication and the U4 leak scan, pass the resulting `SyntheticItem` sequence to
`folio_eval.synthesize.build_corpus`. That builder validates scoreability, routes no-match rows to
their separate slice, checks leakage, and emits the immutable versioned corpus and manifest.
